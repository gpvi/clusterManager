# 当前状态与问题清单

## 1. 当前项目状态

从仓库内容和源码看，这个项目已经具备“真实可运行”的主路径：

- 有 CLI 入口
- 有配置读取
- 有 Podman 容器创建
- 有 Redis Cluster 建群逻辑
- 有 slot 分配和扩容迁移
- 有若干测试文件和设计文档

但它仍更接近“实验环境编排工具”，还不是已经收敛完成的生产级工具。

## 2. 文档与实现不一致的地方

### 命名不一致

- 这个问题已经部分修复：CLI 已统一为 `shards` 和 `nodes-per-shard`
- 为兼容旧脚本，`shaderNum` 和 `replica` 仍保留为废弃别名
- 部分说明仍沿用旧目录名 `redisStudy`
- `DESIGN.md` 里的部分文件名和当前仓库不完全一致

### 运行时文件名不一致

- 代码当前默认写入的是 `run_time_config.yaml`
- 部分代码注释或旧说明仍提到 `json`

### 目录描述过时

- 设计文档中的项目结构与当前仓库并非完全同步

## 3. 已发现的技术风险

### Podman 远端运行的复杂度仍然偏高

这个问题已经从“完全不可用”修到了“可以真实运行”，但复杂度仍然不低。

当前项目现在支持：

- 从 `podman system connection list` 自动探测默认连接
- 读取远端连接所需的 `Identity`
- 在 Windows 客户端上连接 Podman machine / WSL 里的远端 Podman service

当前代价是：

- 仍需要理解本地路径和远端 Linux 挂载路径的差异
- 调试门槛高于单机本地容器 runtime

### 跨平台适配仍未彻底收敛

下面这些关键项已经进入统一配置层：

- Podman endpoint
- Podman 网络名
- Redis 默认端口
- 运行时状态目录
- 运行时文件名

仍然值得继续优化的点：

- CLI 参数优先级和配置优先级的统一规则
- 远端 Linux 路径与本地 Windows 路径的显式区分
- 创建前更细粒度的环境自检

### 全局配置较多

`model/config.go` 通过一组全局变量保存配置，带来的问题：

- 测试隔离困难
- 状态来源不够直观
- 多集群或多实例场景不易扩展

### 运行状态文件管理已改善

运行时状态现在按集群名分目录保存：

- `runtime/<clusterName>/containers.json`
- `runtime/<clusterName>/run_time_config.yaml`

这样多个集群的状态文件不会互相覆盖。

### 关键配置提取仍不完全

当前已经提取出来的配置包括：

- Redis 配置目录
- Redis 数据目录
- 运行时状态目录
- Podman endpoint
- Podman 网络名
- Redis 默认端口
- 镜像名
- 运行时文件名

仍然散落在代码中的关键策略主要还有：

- 容器 bus port 计算方式
- 创建 / 扩容等待重试次数

这会让“改环境”变成“改代码”，维护成本会明显升高。

### 创建前校验过于粗糙

这个问题已经部分修复：

- 创建前现在只检查同名集群是否已存在
- 不再因为机器上有其他无关容器就拒绝创建
- 创建中途失败时也会尝试自动回滚当前集群的残留容器

### 扩容链路仍存在一定时序抖动

在当前环境下，`create`、`scale`、`delete` 都已经实机通过，但 `scale` 过程中仍出现过一次节点短暂未 ready 导致的重试型失败。

## 4. 测试与验证现状

我在当前环境实际执行并验证后，默认测试可以通过，但需要使用上游兼容 tag：

```powershell
go test -tags containers_image_openpgp ./...
```

额外说明：

- `model` 下真实依赖 Podman 的测试已转为显式集成测试
- 当前已经实机验证通过：
  - `TestCreatePodmanConnectionReal`
  - `TestCreation`
  - `TestAddAction`
  - `TestDeleteAllAction`
- 需要真实联调时，再加 `integration` tag 运行

## 5. 如果要继续维护，建议优先级

建议优先处理下面几项：

1. 继续清理代码内部残留的历史命名
2. 给创建 / 扩容 / 删除补更稳定的等待、重试和回滚策略
3. 收敛全局配置变量，降低状态耦合
4. 继续补环境自检和脚本化实机测试入口

## 6. 适合当前项目的定位

如果后续继续推进，这个项目更适合定位为：

- Redis Cluster 学习型工具
- 本地单机实验环境编排器
- Redis Cluster 自动化流程原型

如果目标是生产可用，还需要补：

- 更稳的配置体系
- 更清晰的状态持久化
- 更严格的集群校验
- 更完整的自动化测试
