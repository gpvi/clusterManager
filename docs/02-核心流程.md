# 核心流程

## 1. 创建集群

入口：`cluster create`

核心流程如下：

1. 初始化配置 `InitConfig()`
2. 创建 `ClusterManager`
3. 扫描当前 Podman 中已有容器
4. 只在发现同名集群已存在时拒绝创建
5. 创建一批 Redis 容器
6. 选择一个节点作为登录节点，对其他节点执行 `CLUSTER MEET`
7. 拉取 `CLUSTER NODES` 信息，更新内存拓扑
8. 计算并设置主从关系
9. 给所有 master 分配 16384 个 slot
10. 将运行时信息写入 `runtime/<clusterName>/containers.json` 和 `runtime/<clusterName>/run_time_config.yaml`

### 创建时涉及的关键方法

- `CreateClusterAction`
- `ClusterManager.CreateCluster`
- `ContainersManager.CreateContainers`
- `ClusterManager.MeetNodes`
- `ClusterManager.SetAllNodeRole`
- `ClusterManager.AllocateSlots`

### 主从分配方式

当前实现里，节点先按 IP 排序，再按顺序切分：

- 前一段节点当 master
- 后一段节点按固定数量挂到对应 master 下面

这意味着它更偏“规则式分配”，而不是根据故障域、机架、资源均衡做智能调度。

## 2. 删除集群

入口：`cluster delete`

核心流程如下：

1. 初始化配置
2. 删除 `runtime/<clusterName>/run_time_config.yaml`
3. 删除 `runtime/<clusterName>/containers.json`
4. 枚举 Podman 中全部容器
5. 根据容器标签 `clusterName` 过滤
6. 对命中的容器执行 stop / remove

### 删除逻辑特点

- 删除是按容器标签做筛选的
- 运行时文件已按集群目录区分
- 当前实现已经支持同一宿主机上保留其他无关容器

## 3. 扩容集群

入口：`cluster scale`

核心流程如下：

1. 初始化配置
2. 读取 `runtime/<clusterName>/run_time_config.yaml`
3. 恢复 `nodes_per_shard` 和端口配置，并兼容旧字段 `replica`
4. 重新扫描现有容器信息
5. 从已有节点拉取当前集群拓扑
6. 新增一批容器节点
7. 执行 `CLUSTER MEET`
8. 给新节点补上主从角色
9. 找出没有 slot 的新 master
10. 从已有 master 向新 master 迁移 slot

### 扩容涉及的关键方法

- `ScaleClusterAction`
- `UpdateAfterMeet`
- `UpdateAfterSetNodeRole`
- `UpdateSlots`
- `AddShards`
- `MigratesSlotsToEmptyNode`
- `MigrateSlot`

## 4. slot 迁移逻辑

`MigrateSlot()` 的实现思路是标准 Redis Cluster 扩容流程的简化版：

1. 目标节点设置 slot 为 `IMPORTING`
2. 源节点设置 slot 为 `MIGRATING`
3. 使用 `CLUSTER GETKEYSINSLOT` 获取 key
4. 使用 `MIGRATE` 把 key 迁到目标节点
5. 在源/目标节点更新 slot 归属

## 5. 同步与校验机制

代码里有几处“重试式校验”：

- `waitForMeetSync()`：等待节点互相发现完成
- `verifyNodeTypeSet()`：等待主从关系同步完成
- `VerifyAllocateSlots()`：检查 slot 是否完成分配

这说明作者已经意识到 Redis Cluster 在节点发现、角色同步和 slot 收敛上有异步传播问题。

## 6. 流程上的注意点

结合实现，当前流程有几个值得留意的地方：

- 创建前现在按 `clusterName` 判断同名集群是否已存在，不会因为机器上有其他无关容器就拒绝创建
- 扩容依赖 `runtime/<clusterName>/run_time_config.yaml`，如果该文件丢失，扩容无法恢复上下文
- 创建链路现在已支持 Podman machine 的远端 SSH 连接、Linux 风格挂载路径和 bridge 网络
- 现在命令层已统一使用 `shards` 和 `nodes-per-shard`，但部分底层运行时文件仍保留对旧字段的兼容读取
